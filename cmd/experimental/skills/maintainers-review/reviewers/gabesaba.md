# gabesaba: review profile

gabesaba was a core contributor and approver for scheduling in Kueue (reviewer from 2025-01, approver from 2025-08). They stepped down on 2026-06-01 (#11834) and are now listed under `emeritus_approvers` in `OWNERS`, so where a current maintainer (mimowo, tenzen-y, sohankunkerkar, mbobrovskyi) has decided differently, the maintainer's decision wins; the rules below mark the asks that were overruled. In the data (2024-02 to 2026-05) they built Hierarchical Cohorts, Fair Sharing over hierarchies, and the snapshot/resource-node accounting, and later helped run releases (image verification, "release lgtm", KEP priority lists). The review data has 441 threads (350 PRs, 91 issues), 114 of them their own PRs. They wrote 1630 entries: 936 inline, 632 top-level comments, 62 review summaries. On other people's PRs there are 892 non-command entries, 611 of them inline. Their inline comments land mostly in `pkg/scheduler/preemption` (~90), `pkg/cache/tas_flavor_snapshot.go` (~45), `pkg/controller/core` (~44), `pkg/scheduler/flavorassigner` (~37), `pkg/controller/tas` (~33), docs under `site/content` (~28) and `pkg/cache/cache.go` (~27). Activity peaked in 2025 (429 of the 611 inline review comments).

## What they care about most

Shares are of the 611 inline review comments on others' PRs (keyword tagging, with manual reading as a check; one comment can carry several tags).

1. **Readable control flow (~20%)**: guard clauses, extracting well-named functions, declaring variables close to their use, no throwaway intermediate variables or redundant special-case guards.
2. **Precise, consistent naming (~10-15%, the keyword count is noisy)**: the name must match what the code does, descriptive rather than short names, no vague package names, consistent capitalization of Kueue kinds and notation, API and metric names users can't misread.
3. **Minimal diff and tight scope (~14%)**: revert unrelated changes and debug leftovers, delete unused code, don't export what no other package uses, split refactors into their own PRs, no drive-by renames.
4. **Tests that prove the change (~13%)**: cover every new branch and every new enum or reason value, check that tests fail without the fix, use fixtures that exercise the new path, name tests after the expected result, keep fixtures and tables lean, check for flakes.
5. **Accurate comments, docs and docstrings (~10%)**: document non-obvious logic and why it is there (their most frequent comment request), fix comments that no longer match, link the issue behind a special case, keep TODOs actionable, make user docs and KEPs state the exact behavior and interactions.
6. **Simplicity over generality and code placement (~8%, counting reuse)**: no unneeded generics, indirection, booleans in signatures or premature optimization. Reuse existing helpers, put code in the package that owns the concept, bundle values that travel together, shape helper signatures around their callers, keep predicates to filtering.
7. **Correctness and invariant questions (45% of inline comments contain a question)**: nil cases and nil/non-nil combinations, impossible states made loud, Cohort cycles and hierarchical Cohorts, lending limits, snapshot revert, determinism, shared vs copied data, swallowed errors.
8. **API shape (~6%)**: make invalid states impossible to represent, use enums, don't change the API when the cache is enough.

Logging (~8%) sits at the same weight as simplicity but is narrower: key/value pairs, a `V(n)` level, spelled-out keys.

Form: 16% of inline comments are GitHub `suggestion` blocks and 14% start with "nit".

## How they review

- **Many small inline comments, often as code.** They write many short inline comments: 16% are `suggestion` blocks, and they often sketch whole functions (merge, ancestor walk, enum layout). The tone stays mild: "nit:", "consider", "how about", "can we". About 45% of inline comments are questions ("is this used?", "how come this can be deleted?", "Does this result in the following subtle bug?").
- **They test their own suspicions.** They delete lines and rerun the tests, reproduce reported issues, and link commits from their own fork to show an approach (https://github.com/kubernetes-sigs/kueue/pull/4635, https://github.com/kubernetes-sigs/kueue/pull/7015).
- **Partial passes on large PRs.** They label them ("a few nits to start with", "another partial pass", "First pass."). They also pile nits onto a pending round ("I added a few more nitpick comments, since a rebase is needed anyway :)", https://github.com/kubernetes-sigs/kueue/pull/4581).
- **Before /lgtm** they want: new branches covered, test names fixed, unrelated changes reverted, and their review threads answered. Their closing note is usually short: "/lgtm" plus "thanks!", "thanks for the cleanup :)" or "thanks for addressing all of the comments!".
- **Approval etiquette.** They often combine /lgtm or /approve with "/hold in case @tenzen-y or @mimowo have any comments", or leave one of the two labels to another reviewer ("will leave approval for @mimowo"). About 158 /lgtm, 62 /approve and 23 /hold appear in their entries.
- **What they let go.** They concede readily: "I'm fine leaving it as it is, then", "I'll leave this up to you", "If not, this is not a major objection", "The diff generated by this part isn't so bad. I don't think it is worth the effort at this stage". They accept deferral to follow-up PRs, they withdraw their own suggestions ("ignore above comment please", "After seeing the result, I think the generics was the wrong call, as it just makes the code too complex."), and they invite pushback ("please push back if something I wrote looks wrong :)").
- **On issues** they reproduce the bug, explain the root cause with permalinks to the code, and suggest workarounds before a fix lands (https://github.com/kubernetes-sigs/kueue/issues/3779).
- **As an author** they do what they ask of others. They split prep PRs out, post compare links between pushes, leave "note to reviewers" comments, report coverage numbers, run flaky tests 128 to 256 times, and put the release note for a multi-PR feature on one PR.

- **2024 (109 inline review comments).** The focus was test-suite cleanup after the resource accounting refactor: express state through the API, not internal fields, and keep the original test numbers. Tests (25% of comments) and naming (22%) dominated. - **2026 (73 inline, more top-level).** They did less line-by-line review and more release management (image verification, "release lgtm"), KEP triage, and design input on batching, performance and leader election. Logging (8%), performance (11%) and scope/follow-up (7%) comments go up. "/approve + /hold for another reviewer" becomes the common pattern. ## Author checklist

- [ ] Nested `if`s become guard clauses; no double negatives; booleans are named positively.
- [ ] Compound conditions and long multi-step blocks are in well-named functions or variables.
- [ ] No special-case guards (`len == 0`, nil-before-compare) that the main logic already handles, confirmed by tests passing without them, and no new defensive line without a test that needs it; loops range directly over values, sets and `PathParentToRoot`.
- [ ] Variables are declared right before use; `err` is scoped; no throwaway intermediate variables, always-same parameters, or signature changes made for one caller or for tests.
- [ ] Go idioms in touched code: `(value, error)` order, accessors such as `GetAnnotations()`, `== ""`; maps and strings aren't passed by pointer.
- [ ] Every renamed or changed function still matches its name; names are descriptive rather than short.
- [ ] Kueue kinds are capitalized consistently in code comments and docs; units, quotes and `By` steps are consistent within a file.
- [ ] No magic numbers or boolean pairs in signatures; internal enums use `iota` and each value has a comment.
- [ ] Doc comments sit above functions, cover edge cases (no fit, root excluded), and match the code after refactors.
- [ ] Comments say why a branch or policy exists and link the issue or KEP for special cases; every `TODO` says what and when (`TODO(#N)`), with no scratch `todo` notes left.
- [ ] User docs, KEPs and API comments state exact behavior (required/optional, must/should, scope) in tight prose.
- [ ] Logs use key/value pairs, a `V(n)` level, spelled-out lowerCamelCase keys (`clusterQueue`, `nodeName`) and short messages.
- [ ] No silently swallowed errors (log, return, or say why it is safe); there's a nil check where nil is possible and no error return where failure is impossible.
- [ ] Edge cases (no fit, zero quantity) and every nil/non-nil input combination are handled explicitly; impossible states are commented or logged at V(0)/V(1) instead of returning a silent nil or plausible default, with no checks for invariants that API validation guarantees; ordering has a deterministic tie-breaker; shared data is deep-copied only where it is mutated.
- [ ] Hierarchy walks check for Cohort cycles; quota math uses the existing simulate/revert helpers; the design covers hierarchical and implicit Cohorts.
- [ ] Each new branch fails some test when removed locally; every new enum/reason/metric value is tested; the bug scenario is tested through the whole operation (scheduling cycle, `Reconcile`) with a fixture that exercises it.
- [ ] Test names state the expected result; fixtures are minimal and built from API objects, with no no-op steps, constant table fields or new single-case tables (add the case to an existing table); a single `cmp.Diff` is used in expectations, reusing existing constants and adding no new `EquateEmpty()`.
- [ ] New integration/e2e tests were run about 100 times locally (`GINKGO_ARGS="--repeat=N"`) without flakes.
- [ ] No API change where a cache-only change is enough; invalid or unsupported combinations are unrepresentable or rejected at validation time (CEL markers or webhook), not in the scheduling cycle.
- [ ] API fields, enum values, modes and metrics have names users can't misread; new KEP terms are defined.
- [ ] KEPs describe interaction with TAS, flavor selection and Fair Sharing (a section, or a goal/non-goal).
- [ ] Existing helpers are reused, and new helpers replace all repeated call sites; helpers absorb repeated nil checks (and, in tests, conversions) and return what callers use; new code lives in the package that owns the concept (for example `pkg/scheduler/preemption/policy` for shared ordering); no speculative generics or optimizations; new predicates only filter, and reconciliation happens in `Reconcile`.
- [ ] The diff has no unrelated whitespace, renames, return-type tweaks or debug edits, no code left without a caller, and nothing new exported that no other package uses; refactors and needed renames are in separate or preparatory PRs (a commit split alone is lost at squash merge); each review comment is applied to every occurrence in the PR (and to other places with the same bug), not just the flagged line; cleanups of untouched code go to a follow-up.
- [ ] The release note is short and concrete for upgraders; title, description, `Fixes #N` or `Part of #N` (in the PR body, not in commit messages) and limitations are accurate.

## Method

- **Data.** All of this reviewer's PR and issue comments in kubernetes-sigs/kueue up to
  2026-11-24 (inline review comments with their diff hunk, review bodies, and
  top-level comments), each read together with the surrounding thread. Bot comments
  are excluded.
- **Analysis.** Theme shares come from keyword statistics over all of the reviewer's
  comments, checked by close reading of threads sampled across every year and area.
  Treat the shares as rough weights: themes overlap and keywords miss paraphrases.
- **Evidence.** Every quote is copied from the comment it links to, and each link was
  resolved through the GitHub API by matching the quote against that reviewer's
