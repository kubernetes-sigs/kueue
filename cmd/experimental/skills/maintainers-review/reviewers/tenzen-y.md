# tenzen-y: review profile

tenzen-y is active in the review data from late 2022 (first entries 2022-11/12) to 2026-11. They act as an approver: 2,932 `/lgtm`, 2,893 `/approve`, and 2,653 entries where both are posted together. They also do release management: 801 `/cherrypick` commands, 516 `/release-note-edit` rewrites (on 446 PRs), 235 `/hold`, and regular "I confirmed the promoted image works well" checks on released images and charts. The review data covers 5,951 threads (4,875 PRs and 1,076 issues; 641 PRs are their own) and 18,479 own entries (7,977 comments, 6,870 inline review comments, 3,632 review bodies). Volume grows every year: 333 entries (2022), 2,544 (2023), 3,913 (2024), 5,376 (2025), 6,313 (2026). Where inline comments land: KEPs 24%, other `pkg/` 14%, scheduler and cache 12%, jobs and jobframework 10%, tests 10%, build/CI/Helm/cmd 9%, API types 7%, docs/site 7%, MultiKueue 3%. The most-reviewed areas are KEP design (TAS, DRA, MultiKueue, concurrent admission, configurable preemption), the scheduler and cache, jobframework and the integrations, the Config and Kueue APIs, Helm, and the release process.

## What they care about most

Shares are of the 11,351 "substantive" own entries, meaning not prow commands only and longer than 25 characters. They come from regex matching, so treat them as rough.

1. **Concrete `suggestion` blocks for small fixes**: 17% of entries (1,934). These are wording in docs and comments, renames, signatures, and test tables.
2. **API shape and conventions** (fields, `+optional`/`+required` and `omitempty`, validation (strict first, relaxed later), CEL, `Ref` suffix, kind-prefixed type names, API versions, Alpha/Beta semantics): about 10%, the highest share in 2025.
3. **Justification questions** ("Why do we need…", "Is there any reason…", "Do we need to expose…"): about 6% (691), steady in every year.
4. **Release notes, cherry-picks (what may be backported) and user-facing impact**: about 10% combined. They rewrite notes themselves (516 notes; about 360 start with an area prefix like `TAS:` or `Helm:`; 26 contain `ACTION REQUIRED`).
5. **Test structure and coverage** (table-driven tests with maps, comparing errors rather than messages, no test helpers, callbacks or anonymous functions, plain wrappers, adding cases to existing tests, Ginkgo idioms such as `g gomega.Gomega` and `GinkgoHelper`, picking the right level among unit, integration and e2e): about 6%. This theme grew sharply in 2026.
6. **KEP-first design and scope** (KEP updates, `kep.yaml` milestones and approvers, user stories, stated limitations, yes/no graduation criteria and Alternatives, designs that cover all integrations, one mechanism per user scenario, separate or follow-up PRs without drive-by edits): about 5% KEP/design plus 3% scope. Scope comments doubled in 2026.
7. **Feature gates and upgrade safety** (guard new Alpha logic, FG state on release branches, keep today's defaults, breaking changes): about 3% FG plus 2% upgrade. In 2026 FG mentions rise to 5%.
8. **Logging** (verbosity level, propagated logger, structured key/values, `klog.KObj`): about 2%, but the requests are very consistent. Since 2026-10 the repo's Logging Policy settles the levels.
9. **Go idioms in production code** (no logic in local closures, early return without `else`, named constants instead of literals, nil rather than empty slices, field-named getters, typed values instead of strings, import aliases, compile-time interface assertions, full names for long-lived identifiers, deleting unused code): about 1.5% (about 150 entries). Many are bare `suggestion` blocks, so the share undercounts them.

## Rules for authors

### Naming and style

- **[simple] Don't hold logic in a local closure (`x := func(...) {...}`) inside a function, and don't pass callbacks that mix concerns. In production code, write a named function in the same file. In tests, use wrapper chain methods or `Clone()` of a base object instead of builder closures, callbacks, or `func` fields in test cases (see the inline-objects rule under Tests).** Short predicate literals passed straight to `slices.IndexFunc`/`ContainsFunc`/`DeleteFunc` are fine (they suggest them themselves: #4200, #6203, #15433, 2025–2026), and so is a closure that is the returned value, such as a revert function (#14794). Why: about 35 entries in about 30 PRs, 2025–2026, mostly tests (#5587, #6570, #8431, #8452, #10359, #13573, #14191, #15648, #16398, #18594, #19374); production code in 5 PRs (#4256, #14154, #14918, #15640, #15885). `writing_tests.md` also forbids fixture closures. ## How they review

- **Suggestion-driven.** 17% of substantive entries carry a ```` ```suggestion ```` block, often without any text, so the author can apply it with one click. By file type: Go code 574, test code 527, Markdown/KEP/docs 531, Go comments 117, YAML 96, shell 57. About 60% are small edits (more than 85% similar to the original line).
- **Questions before demands.** Typical openers: "I'm wondering if we can…" (129), "Why do we need…" (108), "Is there any reason…", "Could you…", "I guess that…" (213), "IIUC…". When the author explains, they often reply "That makes sense" or "That sounds good to me" (164 "that makes sense").
- **Polite and appreciative.** Messages start with "Thank you for working on this" (about 60) and "Thank you!" (571 standalone). Review bodies are short: "I left some comments", "Basically, lgtm", "Almost LGTM and left some questions for confirmation."
- **Approver behaviour.** `/lgtm` and `/approve` usually come together (2,653 of the 2,936 lgtm entries). They often combine approve with `/hold` to wait for another maintainer, as in [PR #6888](https://github.com/kubernetes-sigs/kueue/pull/6888#pullrequestreview-3258018896) review 2025-09-23: "in case @mimowo wants to leave something". They also hold until release steps finish, or to rerun flaky e2e tests several times, as in [PR #6630](https://github.com/kubernetes-sigs/kueue/pull/6630#pullrequestreview-3139733491) review 2025-08-21: "let us execute test some times." They defer final release-note checks or design calls to mimowo and alculquicondor, and mention offline discussion with mimowo (68 times).
- **Owns the release note.** Rather than asking the author, they rewrite it with `/release-note-edit` (516 notes; `/set-release-note` since 2026-10) and fix `/kind` labels and titles (`/retitle`, `/kind`, `/remove-kind`).
- **What they let go.** Non-blocking nits and structural cleanups are explicitly accepted as follow-ups: "But, I'm ok w/ a follow-up PR." ([PR #13749](https://github.com/kubernetes-sigs/kueue/pull/13749#discussion_r3815644515) inline 2026-08-19 @ test/integration/multikueue/dispatcher_test.go:1). In 2026 they ask `@coderabbitai` to file `kind/cleanup` issues (116 such comments, often "but no one should be assigned", "follow AGENTS.md") instead of blocking the merge. Bug fixes for a release get fast-tracked: "I put this at the head of my queue for this week's release."
- **What blocks.** Missing feature-gate guarding, API or behaviour breaks for existing users, missing tests at the right level, new mechanisms without a KEP, and wrong test structure.
- **Evidence.** They run things themselves (released images, `helm template`, local benchmarks, reproductions) and cite permalinks to code, KEPs and k8s API conventions in their comments. They also ask authors to double-check claims ("Could you double-check?").

## Changes over time

- **2022–2023 (about 2.9k entries).** Line-level Go and test style dominates: error variable names, wrapper naming, `ptr`, `cmp` usage, license headers, kubebuilder webhook markers, import aliases, and nil safety in new integrations (Pod, MPIJob, Ray). Suggestion blocks are about 21% of entries. Docs-site comments are frequent.
- **2024.** Broader design work (MultiKueue, AdmissionCheckStrategy, TAS start, Deployment/LWS integrations, kueuectl). Cherry-pick and release work grows sharply (cherry-pick entries 4%). "Do we need to expose…" questions are rare (under 10) and mostly 2023–2024.
- **2025.** API-heavy KEP review (DRA, MultiKueue Dispatcher, ElasticJobs, AFS) with the highest API share (12%). Release-image verification runs as a routine. Log-level guidance starts.
- **2026 (6.3k entries, the most).** The focus shifts to (a) test hygiene rules (map tables, no helpers or callbacks, add cases to existing tests, compare errors, cmp over gomega), (b) feature-gate discipline and release-branch FG stages (FG share up from 2% to 5%), (c) KEP depth (KEP mentions 162, double 2025), (d) scale and performance, and (e) delegating cleanups via CodeRabbit-filed issues and accepting follow-ups (132 entries mention a follow-up, against 65 in 2025; 31 explicitly accept one, against 3). Release-note rewrites reach 9% of entries. Kubernetes AI policy enforcement appears (co-author trailers).

## Author checklist

- [ ] New Alpha behaviour sits behind a feature gate, with one gate check covering the new blocks; tests set the gate per case and cover both states while it is Beta.
- [ ] No backport is requested for enhancements, non-Alpha API/schema changes or stage changes (bug fixes, minor Alpha improvements and risk-free test or Helm cleanups can go back); backported behaviour changes are planned as Alpha, disabled by default, on release branches.
- [ ] New API fields are justified, follow k8s conventions (`...Ref`, suffixes consistent with sibling fields, state in conditions rather than phases, controller-computed values in `status` with one `spec` writer, no timestamp that duplicates a condition's transition time, no field that repeats information already held, condition reasons that refine existing ones with `DueTo` rather than new condition types), have user-facing docs that use YAML field names and no implementation terms, and have CRD marker/CEL integration tests.
- [ ] Nothing is exported unless another package needs it; no `_` for unused parameters; no near-duplicate helpers; existing utils, callbacks and equality helpers (`Quantity.Equal`, `ptr.Equal`, `equality.Semantic`) are reused; interface implementations are asserted with `var _ I = (*T)(nil)`.
- [ ] Variable names don't repeat the type (`wls`, not `workloadList`); names say exactly what they cover (no vague "generic", "common", "All"; full names for exported and long-lived identifiers); getters have no `Get` prefix; imports follow the alias conventions (stdlib names kept, `gocmp` only next to stdlib `cmp`, `util<name>`, otherwise the package's existing alias).
- [ ] No logic held in local closures or concern-mixing callbacks: named functions in prod code, wrappers and `Clone()` in tests (short predicate literals for `slices` helpers are fine).
- [ ] Early returns without `else` (validation still collects all errors); no hardcoded literals in prod code (existing or file-top constants), and no one-case constants in tests; no `[]T{}`/`make([]T, 0)` initializations; typed values instead of same-typed string parameters; no unused params, returns or single-use helpers; no stray blank lines.
- [ ] User-facing runtime text spells names in full (`TopologyAwareScheduling`, `resourceFlavor`); docs write API objects as PascalCase Kinds (`Workload`; page titles keep spaces) and reuse Kueue's existing terms (all-or-nothing, `within`); code fences name a language; objects are logged with `klog.KObj` under the usual kind key.
- [ ] Every API field has `+optional` or `+required` (required when it always has a value), passes `make lint-api` for CRDs (Config API: required fields without `omitempty`), starts with strict validation and limits (raised with scale evidence or a documented caveat), and has a documented default and a kind-prefixed type name; user-facing reasons and annotations live in the API package.
- [ ] The feature-gate entry links the KEP or tracking issue (not the PR), its `Version` counts backports, and deprecated gates are locked with a removal comment.
- [ ] Log levels come from the Logging Policy's intended-use table (V(2) only for concise summaries, V(3) scheduler progress and main decisions, V(4)/V(5) details and traces); the propagated logger is used; values are structured key/values; level or key changes get `ACTION REQUIRED` in the release note (and a gate if cherry-picked).
- [ ] Comments that restate the code are removed; temporary code carries a `TODO(#N)` with its removal condition and a tracking issue; KEPs describe the design, not source code, except the Go types (with `json` tags, new or changed fields only) of a new API.
- [ ] New cases go into the existing table-driven test of the production function, named `Test<Func>`/`Test<Type>_<Method>`; no per-branch test functions; no unit tests of unexported helpers.
- [ ] Test tables are `map[string]struct{...}`; objects are declared inline with the `pkg/util/testing*` wrappers and carry only the fields the case exercises (1 replica in e2e); no helper or callback builders or one-off constants; time comes from a fake clock.
- [ ] Unit tests use `cmp.Diff`, with `cmpopts.EquateErrors()` for errors and options inside the call, and no new `EquateEmpty()`; no message, substring or bool error checks; errors are injected with client interceptors; per-case state is created inside `t.Run`; wrappers stay plain setters.
- [ ] Ginkgo tests use `func(g gomega.Gomega)` with `g.Expect`, `GinkgoHelper()` in shared helpers, one `It` per scenario (tables only for webhook/CRD tests), no leftover `FIt`/`FDescribe` or `fmt.Print` debugging, and no timeout bumps to hide flakes; an unrelated CI flake is referenced (or filed) as a `kind/flake` issue when retesting.
- [ ] Nil safety is checked where it really panics (writes into nil maps, nil slices), not for plain map reads.
- [ ] Test level is right: unit over sleepy integration tests, integration over e2e when possible, a stated reason for new e2e tests, no emulation in e2e, FG and config enabled only per case.
- [ ] No test-only code in production files.
- [ ] Scheduling performance at scale is considered (large clusters, high throughput, 10K-pod jobs).
- [ ] A new mechanism has a KEP or KEP update first, designed for all integrations, with `kep.yaml` milestones current and approvers from `kueue-approvers` (two in principle), limitations written down (and rejected by validation when the object itself shows them), yes/no graduation criteria naming what Alpha postponed, unchosen options in Alternatives, removed or renamed items kept on record, and no second mechanism for a scenario an existing feature covers; defaults keep today's behaviour (opt-in or gated changes); new controllers work under leader election (`WithLeadingManager` when they set `NeedLeaderElection: false`); unrelated fixes go to a separate PR or follow-up, with no drive-by renames or refactors.
- [ ] Generated Helm templates are changed via `config/` and `hack/processing-plan.yaml`, and RBAC via `+kubebuilder:rbac` markers; tool, action and image versions are pinned; `make verify` (incl. `toc-update`) passes locally before review.
- [ ] The release note has an area prefix, a full sentence ("Fixed a bug where…" for fixes), the FG and its stage, and `ACTION REQUIRED:` for breaking or ops-visible changes; cleanups use `NONE`.
- [ ] Docs and website are updated for user-visible features and gates, on the page that already covers the topic, with a feature-gate Note card and the reader's point of view; new or changed labels and annotations have an entry in `site/data/labels_and_annotations.yaml`; KEP stories have minimal YAML examples; new generic examples use neutral `example.com` names.
- [ ] Commits carry no AI co-author trailers, no `#N`, `Fixes <issue URL>` or @mentions; the PR template is intact, with `Part of` for partial fixes; the PR title and kind match the work; the PR is rebased when it conflicts; each review comment is applied to every occurrence of its pattern; be ready to prepare manual cherry-picks.

## Method

- **Data.** All of this reviewer's PR and issue comments in kubernetes-sigs/kueue up to
  2026-11-24 (inline review comments with their diff hunk, review bodies, and
  top-level comments), each read together with the surrounding thread. Bot comments
  are excluded.
- **Analysis.** Theme shares come from keyword statistics over all of the reviewer's
  comments, checked by close reading of threads sampled across every year and area.
  Treat the shares as rough weights: themes overlap and keywords miss paraphrases.
- **Evidence.** Every quote is copied from the comment it links to, and each link was
  resolved through the GitHub API by matching the quote against that reviewer's
  comments on the PR. Quotes from PRs since deleted from GitHub were dropped.
- Limits: theme shares come from keyword regexes, so they overlap and are approximate. KEP threads (24% of inline comments) were sampled rather than read in full. Quotes are typed `review` when the text sits in a review body in the review data. The repeated release-note texts across PR numbers are cherry-pick PRs. Many 2026-09 entries are reviews of cherry-pick-robot PRs that ask CodeRabbit to file cleanup issues, which may overweight "follow-up" counts.
