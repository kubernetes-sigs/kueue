# ahg-g: review profile

ahg-g co-founded the project with alculquicondor and was its lead approver in the first year. The data runs from 2022-02 to 2024-01, but 91% of their comments date from 2022. The review data has 302 threads (220 PRs, 82 issues) with 1,582 of their own entries: 978 inline, 564 top-level comments and 40 review bodies. 238 entries are bare prow commands. 242 are replies on their own PRs. That leaves 1,102 substantive review comments on 184 other people's PRs, 856 of them inline. Most of those went to alculquicondor (363), kerthcet (252), denkensk (236), ArangoGutierrez (103), mimowo (80) and knight42 (45). The most-reviewed paths are `pkg/queue` (163 inline), `pkg/controller/core` (114), `test/integration/scheduler` (97), `pkg/scheduler` (75), `pkg/cache` (67), the preemption KEP (44), the API types (~90 across v1alpha1/v1alpha2/v1beta1) and `docs/` (~70). They ran `/lgtm` on 152 threads and `/approve` on 66.

## What they care about most

Shares are of the 1,102 substantive comments. They come from keyword matching plus a full read, they overlap, and they are rough.

1. **Smaller, simpler code**: drop unneeded functions, types, flags, return values and checks, inline single-caller helpers, reuse existing helpers, keep APIs narrow (~15%).
2. **Wording of comments, API docs, user docs and KEPs**: say what it means, not how it is implemented (~15%; 110 of their 240 `suggestion` blocks rewrite prose or doc comments).
3. **Test structure and coverage**: ginkgo When/It/By phrasing, `Consistently` vs `Eventually`, wrappers, minimal fixtures with a namespace per test, a test for every bug and every requeue event (~15%).
4. **API semantics and design**: what a field means, where a knob lives, strict validation of new fields, k8s precedent, YAGNI. This dominates their 2022-H2 and 2023 reviews (~12%).
5. **Naming and project terms**: admitted/inadmissible, not scheduled/assigned; kinds written as CamelCase (ClusterQueue); names consistent with sibling functions (~5%).
6. **Messages, events and metrics**: concise log, event and condition messages with context; an Event for each user-visible transition; precise metric help text; k8s condition conventions (~6%).
7. **Cost and correctness at scale**: extra API calls per workload, races between cache and queue manager, cohort-wide effects, idempotency, sibling Create/Update/Delete paths that behave alike (~7%).
8. **PR hygiene**: squash commits (asked in 29 PRs, ~16% of the PRs they reviewed), keep refactors and stray one-line edits out of the PR, split large PRs, say how the change was verified and what a copied or moved file changes, file an issue for out-of-scope findings, coordinate with overlapping open PRs, apply each fix to every occurrence, and address every reviewer's open threads (~5% of comments, plus 32 "ditto" repeats).

## How they review

- **Macro first, then micro.** On larger PRs they first argue about where an option belongs, and only then review lines: "Before reviewing further, I would like to discuss at what level we should have this option" (PR #80). "First round of review, we need integration tests, but lest leave that until we converge on the logic itself." (PR #135).
- **Mostly concrete suggestions.** 240 of 1,102 comments (22%) are GitHub `suggestion` blocks. 68 of them rewrite docs or KEP prose, 42 rewrite code comments or API docs, 26 rewrite log, event or test-failure messages and 32 rewrite test names. Many other comments include a code sketch of the intended shape (PRs #115, #135, #230).
- **Many questions.** About 16% of comments end in a question mark ("why do we need this?", "did the tests fail without those changes?"). They use these to make the author justify each line.
- **Tone.** Collaborative and soft: "lets", "I would", "perhaps" or "may be" appear in about 200 entries, and ":)" in 42. They apologise for back-and-forth ("I am sorry for the back and forth, this plumbing doesn't look "right"", PR #104). They welcome first-time contributors. They are also firm on reliability ("rare is not an argument", "we should never tolerate flakes").
- **Approval.** The usual sequence is "thanks, pls squash" followed by `/lgtm` plus `/approve` in one comment. When a co-owner should weigh in, they write "/lgtm /hold leaving approve to @alculquicondor" (PR #135) or `/hold` "Just so it doesn't get merged by mistake". Before approving they expect review comments resolved, tests for the new logic, docs for user-facing changes and a squashed history.
- **What they let go.** They defer non-essential improvements to follow-up PRs or issues (about 22 comments say "followup" or "separate PR", for example "as a followup, I would put the heap in its own pkg"). They accept an author's alternative when it is reasonable ("since you already did that lets keep it as is", PR #248). They also let migrations happen separately ("we can do the migration for the whole file separately", PR #179).
- **Project management.** On issues they triage (`/help`, `/good-first-issue`, `/kind`), nudge stalled PRs ("friendly ping"), keep checklists of remaining work (#171, #199) and point contributors at the next issue.

- **2022-H1** (710 substantive comments, 64% of the total): line-level review of the core: queue manager, cache, scheduler and integration tests. ## Author checklist

- [ ] A workload is admitted/admissible/inadmissible against quota, never "scheduled", "unschedulable" or "assigned" ("scheduled" is for pods, "assigned" for flavors). "Quota reserved" when admission checks may still be pending.
- [ ] Each name says exactly what the thing is. No package-prefix stutter. Names match sibling APIs (`PushOrUpdate`, `PushIfNotPresent`). Kinds are written as one word (ClusterQueue, not "cluster queue").
- [ ] Short-lived results are scoped to their `if` (`if v, ok := m[k]; ok`). No single-use interim variables, flags or arrays.
- [ ] No named returns, no abbreviations in exported names, no builtin names (`new`) as variables.
- [ ] No wrapper types around plain maps, no duplicate flag-plus-error returns, no error returns that can't fire, no unneeded copies or checks.
- [ ] Single-caller short helpers are inlined; existing helpers are reused, not re-implemented. Signatures take the narrowest input (a key, not the object). Side effects (Event, condition update, `Broadcast`) live inside the function that performs the action.
- [ ] No re-checks of what the callee already guarantees. Early exits keep indentation low. No stray empty lines.
- [ ] Code sits in its conceptual package: object helpers in `pkg/workload` and similar, not in a controller package; single-test constants inside that test. No direct `golang.org/x/exp` imports.
- [ ] No comments that restate names (on API fields, rewrite them instead). Comments explain states, return values, locking, framework mechanics (what triggers `Reconcile`, `cond.Wait`) and why.
- [ ] API doc comments describe user-visible semantics, state cross-field rules (what is included, invalid combinations, nil vs empty), and claim nothing Kueue does not enforce.
- [ ] Every TODO references an issue (`TODO(#N)`), not a GitHub handle.
- [ ] Log, event and condition messages are short, contextual (object, flavor, resource) and structured (`klog.KObj`, `V(n)` per the Logging Policy). No "Successfully" in events. No low-verbosity log on a per-workload event path. ("Failed to" in error logs is fine today.) In the scheduling cycle or a reconciler, a non-critical failure is logged, not a reason to abort; system errors keep their `log.Error`. Lower-level helpers return errors instead of swallowing them.
- [ ] Conditions: one-word CamelCase reason, free-text message, update in place, skip unchanged writes.
- [ ] Every user-visible transition (created, started, stopped with reason, deleted, preempted) emits an Event; no-op paths emit none. Metric help text and `+metricsdoc` label descriptions say what is counted and by which labels (the reference tables are generated, not hand-edited).
- [ ] Ginkgo specs read as `When(...)` / `It("Should ...")` / `By("...")`.
- [ ] "Stays the same" is checked with `Consistently` (with the `behavioral` duration constants), or with one check such as a metric once processing is provably done, never with `Eventually`. No `Eventually` around a synchronous read of an object the test just created. The mutation is not inside the `Eventually` that asserts on its result. No `sleep` to wait for a state change: `Eventually` in integration and e2e tests, a fake clock or a channel in unit tests.
- [ ] Integration tests use a namespace per test (created in `BeforeEach`, deleted in `AfterEach`), reuse `BeforeEach` objects, create nothing unused, create and clean up per-test or modified objects in the test, and refer to objects by `obj.Name` (unit tests may use literals).
- [ ] Tests use `MakeWorkload`/`MakeClusterQueue` wrappers and the framework. Unit tests are table-driven and use `cmp.Diff` with (-want,+got) for structs, plain comparison for scalars. Integration and e2e scenarios are separate `It`s, with `DescribeTable` only for webhook and CRD validation. Each test lives in the package of the code it tests.
- [ ] Every bug fix has a test. Every event that can make a workload admissible is covered. Each new exported or overridden function (not unexported helpers) and each failure path has its own case, checking the condition's reason and message.
- [ ] No extra API call per workload without a stated reason. No full scan where an index or tracked set would do. Effects across the cohort and cache/queue races are considered. Sibling paths (Create/Update/Delete, status updates) behave alike, or the PR says why one differs.
- [ ] New API fields or config have a concrete use case and k8s precedent. New fields get strict validation and considered immutability, using kubebuilder markers or CEL where they fit (including reference name formats) and k8s helpers in webhooks only for the rest, on the spec fields users set, with exact field paths. Validation of a field that already shipped is not tightened without a plan for existing objects.
- [ ] A KEP lists Non-Goals and unsupported cases, and grounds new APIs in CUJs or other batch schedulers.
- [ ] User-facing changes update the concepts and tasks pages under `site/content/en/docs/` and call out caveats users would trip on. Prose is spell-checked; headings are plain, use exact API names, and are never empty.
- [ ] Unrelated refactors and stray edits to comments, test values or manifests are reverted or moved out, out-of-scope findings have a linked issue, history is squashed, each review fix is applied to every occurrence in the PR, every reviewer's open threads are addressed and replied to before asking for another review, and any flake is fixed or has an issue.
- [ ] The PR description says how the change was verified and, for copied or moved code, what differs from the source. Overlapping open PRs and issues were checked first.

## Method

- **Data.** All of this reviewer's PR and issue comments in kubernetes-sigs/kueue up to
  2026-11-24 (inline review comments with their diff hunk, review bodies, and
  top-level comments), each read together with the surrounding thread. Bot comments
  are excluded.
- **Analysis.** Theme shares come from keyword statistics over all of the reviewer's
  comments, checked by close reading of threads sampled across every year and area.
  Treat the shares as rough weights: themes overlap and keywords miss paraphrases.
- **Evidence.** Every quote is copied from the comment it links to, and each link was
  resolved through the GitHub API by matching the quote against that reviewer's
  comments on the PR. Quotes from PRs since deleted from GitHub were dropped.
- **Limits:**
  - The extract labels each entry with the PR author, not the entry author, so the per-author counts are per-PR-author.
  - Keyword buckets are noisy. For example, "package placement" also matches links containing `pkg`.
  - About 80% of the data predates v1beta1. Many rules refer to files that no longer exist (`api/v1alpha1`, `queuedworkload_controller.go`).
  - Their own-PR replies show what others asked of them, not their own bar, so I excluded them from the theme shares.
  - All quotes are copied verbatim, including original typos.
