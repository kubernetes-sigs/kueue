# alculquicondor: review profile

Founding maintainer and approver, now emeritus. The review data covers 2022-02-16 to 2024-10, plus 6 stray entries up to 2025-03. It has 11,063 of their own entries across 2,039 threads (1,564 PRs, 475 issues): 6,255 inline review comments, 4,143 top-level comments and 665 review bodies. 434 of the threads are their own PRs or issues (KEPs, v1beta1 API, preemption, docs). 5,540 of the inline comments are on other people's PRs, spread over 777 PRs. Inline comments by area: KEPs about 12%, site/docs about 14%, integration/e2e tests 9%, unit tests 9%, scheduler/cache/queue about 13%, job integrations and jobframework 11%, `apis/` 7%. The rest are admission checks (ProvisioningRequest, MultiKueue), `kueuectl`/`kjobctl`, Makefile/hack/config and `cmd/`. Inline comments are short (median 13 words). 21% of them are GitHub ```` ```suggestion ```` blocks.

## What they care about most

Shares are hand-coded from a random sample of 150 inline comments on others' PRs, cross-checked with regex counts over all 6,255 inline comments. Ordered by share.

1. **Wording of docs, KEPs, API comments and user-facing text** (~20%). Many small `suggestion` rewrites of site pages, KEP prose and field docs, cross-links between docs pages (the most frequent docs ask), the Kubernetes docs style (active voice, "you"), vendor-neutral docs, plus about 90 suggestion blocks that only fix a one-word typo.
2. **Tests: right level, readable assertions, coverage of the change** (~15%; about 105 inline "add a test / coverage" asks over 75 PRs). Unit vs integration vs e2e, table-driven inputs/outputs, error comparison with `cmp.Diff`.
3. **Correctness and behaviour edge cases** (~13% of sampled inline comments; ~17% of all inline comments are questions). Typical questions: "what happens if…", "why remove this check?", missing state transitions, NotFound handling, restarts.
4. **Logs, events, condition messages and errors** (~6% + ~4.5% error handling). Contextual logger, structured messages, verbosity, no duplicated keys, messages a user can act on, and no silently discarded errors.
5. **Simplify, remove, reuse** (~10%). Unneeded variables, functions, indirection or tests, and nothing added before it has a user; use existing helpers (controllerutil, `apimeta`, `ptr.Deref`, `pkg/util`). Closely tied to API-server load: batched status writes, no API calls in handlers, indexed reads.
6. **Naming and exported surface** (~8%; ~5.5% of all inline comments mention renaming). Go getter style (no `Get`), names that say what a thing is, unexport when possible.
7. **API semantics, defaulting/validation, feature gates, upgrades** (~6% inline; dominant in KEP threads). Field godoc that explains null/default behaviour, backwards compatibility, Kubernetes API conventions (enums over bools, lists over maps, `...Seconds`; now partly enforced by kube-api-linter, `make lint-api`), and admission-time validation of immutable fields.
8. **PR scope and release hygiene** (~5% inline, most of the top-level comments). Separate PRs for unrelated changes and preparatory refactors, accurate PR descriptions, release notes (with `ACTION REQUIRED` when users must act), manual verification in a live cluster, cherry-picks.

## How they review

- **Inline-first and concrete.** A third of the activity is short inline remarks, and 1 in 5 inline comments is a ready-to-apply `suggestion` block. Large PRs get dozens of comments in one pass (PR #1072: 111, PR #1319: 97, PR #849: 96). Big PRs are reviewed in stages ("Some initial comments.", "Just missing reviewing the integration tests").
- **Questions over orders.** About 17% of inline comments end with "?". Common openers: "I think…" (138), "can you…" (71), "I don't think…" (61), "why not…", "what happens if…", "do we need…". Authors are invited to push back, and they often concede when the author explains ("No, that's ok. Thanks for explaining.").
- **Explains with upstream conventions.** Links to the Kubernetes API conventions, the structured-logging guide, Effective Go, and k/k code (about 270 GitHub links in inline comments).
- **Approve with a hold for nits.** In 67 comments `/approve` is paired with `/hold` ("in case you want to do the nit", "Just some nits and clarifications"), so the author fixes the nits and unholds. Holds are also used for release timing, waiting for a dependent PR, or repeated CI runs ("for ten integration runs", "Integration passed 1/5").
- **Approver role in later years.** `/approve` without `/lgtm` appears 296 times, often with "I'll leave the LGTM to" or "Leaving LGTM to" another reviewer who knows the area (about 44 comments).
- **Before approving, they want to see:** tests at the right level for every changed path, a correct release note (often rewritten by them), unrelated changes split out, commits squashed (2022–2023), CI green or the flake filed, and sometimes real output ("Please share how these log lines look.").
- **What they let go:** nits marked "nit" or "for a follow up" (about 110 inline "follow up" mentions: "Let's add a unit test for this function in a follow up."). Pointer-vs-value preferences when the author feels strongly. Renames are kept for later PRs to keep diffs small.
- **Tone:** brief, friendly, sometimes with an emoticon (":)" is frequent), and never personal. Firm on correctness and API semantics.

## Author checklist

- [ ] No `Get`/`Set` prefixes; names say what they hold; vague names (`info`, `result`) replaced.
- [ ] Nothing exported without an outside caller, and nothing added without a user; single-caller helpers live next to the caller or are inlined; code sits in its type's file.
- [ ] Typos fixed in identifiers, test names, `ginkgo.By` strings, logs and docs; Go file names in snake_case; inclusive wording.
- [ ] Imports use the codebase's established alias, and no new alias without a name collision; early returns instead of `else`; `var x []T` and `len(x)` checks; positive boolean names; no new package-level variables.
- [ ] Logger comes from `ctx` (or `logr.Logger` by value); no duplicated context keys; constant capitalized message, camelCase keys, `klog.KObj`, sensible `V(n)`.
- [ ] Event, condition and status messages are short and actionable for users and do not name their own object; detail goes in logs; no event the status already covers.
- [ ] No error discarded with `_` (tests fail on it, ignored ones explained); errors do not repeat context the caller or field path adds; `%w`; validation returns all errors in a `field.ErrorList` with the right constructor.
- [ ] Non-obvious code has a "why" comment (and a source link for code copied from k/k); comments match the code; TODOs say what to do (with an issue); no design essays in comments.
- [ ] API fields: godoc starts with the JSON name and covers null/default behaviour and exclusivity; validation does not assume defaulting; gated fields dropped or ignored (not rejected) when the gate is off, and both gate states tested.
- [ ] Objects created by older versions keep working; new or risky behaviour behind a feature gate (long-term switches go in config).
- [ ] API conventions: enum over bool, lists of named subobjects with `listType`, `...Seconds` durations in CRDs (run `make lint-api`); immutable fields enforced at admission (CEL `XValidation` for Kueue CRDs, `ValidateImmutableField` in Go webhooks).
- [ ] Docs: active voice and "you", concepts cross-linked, CamelCase kinds, prerequisites in "Before you begin", gated features documented (`owner:` and `kep:`/`issue:` header in `kube_features.go`, gate named in godoc, `feature-state` on the page); vendor-neutral, with vendor guides on the Ecosystem page; full samples via `include`, version via `param`, released operator versions; no implementation details in docs, godoc, KEPs or release notes; design agreed in a KEP (or detailed description) before the code, and the KEP updated when the implementation changes it.
- [ ] Existing helpers reused (`controllerutil`, `corev1` constants, `maps`/`slices`, `pkg/util`, test wrappers); no `x/exp`.
- [ ] One write per object part (status, or spec) per change, none if nothing changed, none in event handlers; indexed or selector reads, no List-all; related cache state read under one lock; metrics recorded after the write succeeds.
- [ ] No loop-invariant work, throwaway slices/maps/clones in hot paths, or unneeded indirection; counters instead of re-iterating cache state; no mutation of informer-cache objects; `new(v)`, `ptr.Deref` and `apimeta` helpers used; shared integration logic in `jobframework`, optional behaviour behind a `JobWith…` interface; fixes applied to every sibling integration or usage.
- [ ] Restart path considered: `Create` events for existing objects behave like updates.
- [ ] Tests at the cheapest sufficient level; every changed reconciler path covered, including negative cases and full transitions.
- [ ] No `Eventually` around helpers that already poll; boolean asserts carry a failure message.
- [ ] Unit-test tables only for several similar cases, with explicit inputs and literal `want*` outputs; `ginkgo.DescribeTable` only for webhook/CRD validation tests; results and errors compared with `cmp.Diff`, never as strings.
- [ ] No duplicated or artificial tests; no sleep-based timing or literal timeouts (shared `behavioral` constants); each dependent step waits for the earlier change to be observed; `Consistently` only when needed; fake client instead of a mock client; feature gates set with `SetFeatureGateDuringTest`; assertions on behaviour, not finalizers or internals.
- [ ] Diff has no unrelated or accidental changes; docs, cherry-pickable fixes and preparatory refactors are in separate PRs, and a split series is linked; title and description match the diff; Draft until ready; fixes pushed before threads are resolved.
- [ ] Release note present, user-worded, area-prefixed (or NONE for fixes to unreleased work), with `ACTION REQUIRED:` when users must act; behaviour tests can't show was tried in a live cluster (upgrade included) with output pasted; flakes linked to issues, and flake fixes explain the event sequence; cherry-pick need flagged.
- [ ] RBAC markers for newly read kinds; `make manifests update-helm` (and `make generate` for API changes) run, generated files not hand-edited; new tools pinned in `hack/tools/go.mod`.

## Method

- **Data.** All of this reviewer's PR and issue comments in kubernetes-sigs/kueue up to
  2026-11-24 (inline review comments with their diff hunk, review bodies, and
  top-level comments), each read together with the surrounding thread. Bot comments
  are excluded.
- **Analysis.** Theme shares come from keyword statistics over all of the reviewer's
  comments, checked by close reading of threads sampled across every year and area.
  Treat the shares as rough weights: themes overlap and keywords miss paraphrases.
- **Evidence.** Every quote is copied from the comment it links to, and each link was
  resolved through the GitHub API by matching the quote against that reviewer's
  comments on the PR. Quotes from PRs since deleted from GitHub were dropped.
- Limits: regex themes over- and under-count (for example "name" matches many contexts). The review data has no bot comments, so CI context is inferred. In issue threads (475), all of the reviewer's comments on others' issues were read once (cycle 4), and they are mostly design and support. Own-PR threads are counted in the volumes but left out of the rule evidence.
