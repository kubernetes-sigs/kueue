# kerthcet: review profile

kerthcet was an early, very active contributor (2022-04 onward). They became approver for deps, controllers and webhooks in #808 (2023-05) and are emeritus now. The review data has 341 threads (2022-04 to 2025-06) with 1,513 of their own entries: 827 inline, 623 conversation comments, 63 review bodies. About a third of the threads (108) are their own PRs or issues, so roughly 520 entries are author replies. As a reviewer of other people's work there are 645 substantive PR comments (544 inline) plus 151 issue comments. Activity per year: 706 entries in 2022, 607 in 2023, 165 in 2024, 35 in 2025. By path, the 645 reviewer PR comments split into `pkg/` 27%, tests 19%, KEPs 17%, general PR comments 16%, `apis/` 11%, config/build/helm 6%, docs/site 6%. A few PRs take most of the volume: #1385 LendingLimit implementation (111 comments, 17% of all reviewer PR comments), #362 internal-cert config (46), #421 first e2e suite (36), #667 RayJob (34), #1331 LendingLimit KEP (32), #410 preemption KEP (27), #532 v1beta1 API (21).

## What they care about most

1. **Design and semantics questions, mostly on KEPs and API** (~30% of reviewer comments): user stories, edge cases, "start strict" and the smallest KEP scope.
2. **Test quality** (~20%): test values that actually show the feature works, no redundant cases or setup, changing only what the case is about, a case for each branch, gate state and input variant, `cmp.Diff`/want-objects, building fixtures with the existing wrappers, test names that match the behaviour.
3. **Cosmetic and mechanical nits** (~15%): blank lines, license headers, typos, unrelated reverts, inlining single-use temporaries, removing unused code, ditto-style "same to other places". Much of this is now caught by linters (`goheader`, `misspell`, `dupword`, revive `empty-lines`, `gci`), except typos in KEPs and docs, reverts of unrelated edits, and dead or redundant code.
4. **Comment and doc accuracy** (~10%): explain why, not what; remove meaningless comments and add missing qualifiers to loose ones; put comments on the code they explain; keep method comments in sync; fix copy-paste leftovers and Kind names; polish API field docs and user docs (concise, linked, section order). Often given as `suggestion` blocks (46 on others' PRs).
5. **Naming and placement** (~8%): precise names, alignment with sibling names, plural lists and singular types, renaming types that no longer fit, logic placed in the type that owns the data, reuse of existing constants and values.
6. **Correctness and safety in hot paths** (~8%, nearly all in #1385, with a few in #667, #318 and #1852): out-of-range slice indexes, mutating shared cache state, feature-gate checks first, redundant lookups and allocations.
7. **PR hygiene** (~5%): don't squash during review, split website/docs into another PR, release notes and kind labels.

Shares come from keyword counts plus manual reading; treat them as rough.

## Rules for authors

Each precedent is written as `[PR #N](url) kind date [@ path:line]: "exact quote"`. Every quote is an exact, contiguous substring of one kerthcet comment in the review data. ### Correctness and performance

- **Guard slice indexes that can be out of range, and test that case. Don't add guards before map reads.** In Go a read from a nil map or a missing key returns the zero value and can't panic, so `if m == nil || m[k] == nil { return 0 }` before `return m[k][r]` is dead code. A pointer value read from a map is nil when the key is missing, so its nil check before a dereference stays (see "Don't add types, registrations, nil checks…"). Why: a panic in the scheduler or a controller is fatal. Only 1 slice-index ask (#667), so below the 3-PR bar; kept because it is the correct part of a wider pattern. The other 6 "guard" asks, all in #1385 ("What if  guaranteedQuota[flavor] not found, we'll panic here.", "Plz add defender here"), were nil checks before nested-map reads, which can't panic, and later in the same PR they said the plain read is enough (`pkg/cache/snapshot.go:181` "`return c.GuaranteedQuota[fName][rName]` is enough I think.", `pkg/cache/snapshot.go:212` "Again, no need to lookup twice"). So those are not precedents. The #1852 index comment asked why a loop starts at 1, not for a guard. Today the quota maps are flat (`FlavorResourceQuantities map[FlavorResource]Amount`, `pkg/resources/resource.go:38`).
  - [PR #667](https://github.com/kubernetes-sigs/kueue/pull/667#discussion_r1197971819) inline 2023-05-18 @ `pkg/controller/jobs/rayjob/rayjob_controller.go:153`: "Better to check whether nodeSelector[index+1] is valid here. It's more safe"
- **Never mutate shared cache or snapshot maps, or input objects, in place.** Why: other steps of the scheduling cycle read the same data. 3 comments in 2 PRs (2 in #1385, 1 in #1852), below the 3-PR bar. Kept because current maintainers ask the same (mbobrovskyi on #8125, 2025-12: "We need to deep-copy it to avoid modifying the original object.").
  - [PR #1385](https://github.com/kubernetes-sigs/kueue/pull/1385#discussion_r1425050131) inline 2023-12-13 @ `pkg/scheduler/preemption/preemption.go:350`: "This is not right, because you're changing the underlying value of the cache, which is used through the whole scheduling cycle."
  - [PR #1852](https://github.com/kubernetes-sigs/kueue/pull/1852#discussion_r1598345723) inline 2024-05-13 @ `pkg/controller/core/workload_controller.go:332`: "I suppose not change the original resources, although will not impact the result but may lead to confusion?"
- **In hot paths (scheduler, cache and snapshot, webhooks), compute static values once (in the snapshot or cache, or outside the loop) and avoid double lookups and needless allocations.** Don't add such optimizations to code that isn't hot, such as controller event handlers: mimowo pushed back on that in #11141 (2026-05, "this looks like optimization of a non-hot path.", and "premature optimization" in the review), and called webhooks a hot path in #10796. Why: about 6 comments in 2 PRs (5 in #1385 on the cache and snapshot, plus #318 on a webhook loop), below the 3-PR bar, all on hot code. Overlaps: skipping work when the gate is off is "Check the feature gate first", and returning a map read directly instead of checking it first is "Don't add types, registrations, nil checks…", which applies everywhere.
  - [PR #1385](https://github.com/kubernetes-sigs/kueue/pull/1385#discussion_r1418534024) inline 2023-12-07 @ `pkg/cache/clusterqueue.go:110`: "since the guaranteedQuota is static, can we calculate in advance, and saved in cache rather than calculating each time."
  - [PR #1385](https://github.com/kubernetes-sigs/kueue/pull/1385#discussion_r1430967049) inline 2023-12-19 @ `pkg/cache/snapshot.go:170`: "Why not judge this first? Then no need to allocate the memory for guaranteedQuota."

## How they review

- **First-pass reviewer, then hand-off.** Typical closes: "other parts generally LGTM." followed by `/assign @alculquicondor` (#667 review 2023-05-22), "Looks good to me, leave lgtm to @ahg-g in case he would like to review for another round." (#332 comment 2022-08-17), and `/lgtm` plus "Leave the final pass to @mbobrovskyi" (#5658 review 2025-06-16). On #1385 the main approver waited for them: "I'll wait for an LGTM from @kerthcet before giving another pass." In total: 65 `/lgtm`, 18 `/approve` (some typed as plain "approve" without the slash), 15 `/hold` (for example `/lgtm` `/hold` "In case of other advices." in #618 comment 2023-03-09), and 28 `/ok-to-test` for new contributors.
- **Several short passes on a large PR.** On #1385 they reviewed in about 8 rounds over 7 weeks, saying which parts were not reviewed yet ("The preemption file not checked yet." review 2023-12-07; "Tests now reviewed yet." review 2023-12-13). The 2024-01-09 review ended with "We need more integration tests."
- **Phrasing.** Requests are short and imperative, often with "Plz"/"Please" (31) or "Let's ...", and as `suggestion` blocks (46). "Ditto" / "Same to other places" (18) marks repeated issues. Opinions are framed as "I think" (106 occurrences), and many comments are genuine questions ("right?", "WDYT?"; about 16% of inline comments end in "?"). Authors are thanked often ("Thanks @kannon92 for bringing us e2e test framework, I think we're heading to the right way." #421 review 2022-11-04).
- **On KEPs they raise scenarios rather than demands.** Numbered step-by-step scenarios (e.g. #410, #284), alternatives, and the question of whether a field should be configurable. Their suggestions to add an option or policy were mostly deferred or turned down: #410 `onFailure` (alculquicondor: "This should be handled in the specific job API, not by Kueue."), #742 an opt-out from reclaim (they withdrew it: "We can add when needed, not conflict with current API."), and Issue #1091 `requeuePolicy` (the boolean `active` field won). So "offer an option" is not an author rule. They often concede: "But I'm ok with current implementations for a startup until we come up with more user cases." (#331)
- **What they let go.** Small inefficiencies and stylistic preferences when the author pushes back: "Not a big deal actually, we can revisit this later if necessary." (#846), "If you're intentioned, it's ok." (#489), "I'm ok to miss this case." (#1331). Also first-version tricks in new infra: "I'm ok with it for the first version, until we find a way better." (#421), and organisation nits on large features: "But I don't want to block this significant feature." (#578). Work outside the PR's scope is moved to follow-ups or issues instead of blocking.
- **What they don't let go.** Wrong semantics in cache or scheduler code, possible panics, untested branches, and test values that can't detect the feature.

- **2022 (320 reviewer comments).** Webhooks and validation, the config API (#362: pointers for optional fields, defaults, constants, table tests), and the first e2e suite (#421: blank lines, license, wrappers, cleanup). Many mechanical nits. Also design input on the early KEPs (preemption #410, reclaim #331, all-or-nothing #433).
- **2023 (350).** Integrations and jobframework (MPIJob #578, RayJob #667, #627, #846): interface checks, shared helpers, "be strict at first". Also API docs for v1beta1 (#532), helm and docs PRs, and KEPs (partial admission, plain pods, LendingLimit #1331). Approver from #808 (2023-05).
- **Late 2023 to early 2024.** Deep code review of the LendingLimit implementation (#1385): feature-gate-first, nil safety, no mutation of the cache, precomputing in the snapshot, test values. This is the densest source of correctness rules.
- **2024 to 2025 (111, then 14).** Mostly design questions on KEPs (fair sharing #1773, fair-sharing API #2070, dynamically sized jobs #1852) and comments on serving/LWS and TAS. Hardly any line-level review.
- **Now historical.** Many of their simple nits are now enforced by tooling: license headers (`goheader`), typos and duplicated words in Go files (`misspell`, `dupword`), blank lines at block edges (revive `empty-lines`) and import grouping (`gci`), all in `.golangci.yaml`; pointer optional fields in `apis/kueue/` (kube-api-linter `optionalfields` in `.golangci-kal.yaml`); hand-edited generated RBAC (`make verify` fails on any diff after regeneration); e2e cleanup on failure (`trap cleanup EXIT` in `hack/testing/e2e-test.sh:62`). Two asks now go against the contribution guidelines: "`Eventually` only for async state" (updates that can conflict are retried in `Eventually`) and reusing error-message constants in tests (errors are compared by type and structure, not text). Their Issue #973 preference for reusing `PriorityClass` lost to a Kueue-owned `WorkloadPriorityClass`. Their #667 ask to depend only on released operator versions no longer matches `go.mod`, which pins a spark-operator pseudo-version and a kuberay release candidate. The standards still visible in the code: `var _ jobframework.GenericJob` assertions (10 files under `pkg/controller/jobs/`), pointer optional config fields (`apis/config/v1beta2/configuration_types.go:517`), error-message constants plus `validateLimit` (`pkg/webhooks/clusterqueue_webhook.go:42`, `pkg/webhooks/clusterqueue_webhook.go:381`; tests now ignore the message), a per-Kind `ctrl.LoggerFrom(ctx).WithName(...)` in every integration webhook (`pkg/controller/jobs/job/job_webhook.go:118`), and feature-gate status in API field docs (`apis/kueue/v1beta2/workload_types.go:64`). ## Author checklist

- [ ] Names say exactly what the thing is and match sibling names, test variables included. Rename types, functions or folders your change makes inaccurate.
- [ ] List fields plural, types and interfaces singular. Logic lives in the type that owns the data; no shared helper file for a single user.
- [ ] No unused types, duplicate registrations, redundant nil checks or overwritten assignments. Single-use temporaries inlined; errors asserted with `gomega.Succeed()` (inside `Eventually` for updates that can conflict).
- [ ] No stray blank lines; related `const`/`var` declarations grouped in one block; every file ends with a newline.
- [ ] Existing constants, variables and computed values reused, not redefined.
- [ ] No edits to unrelated lines (blank lines, commas, rewording of correct comments).
- [ ] Comments explain why and sit on the code they explain. Restating comments deleted; loose ones made precise. Method doc comments updated when behaviour changes; new struct fields documented.
- [ ] Exact Kind names in docs, comments and logger names; code copied from another integration has no leftover Kind names, logger names or checks that don't apply.
- [ ] API field docs state constraints and the alpha/feature-gate status.
- [ ] User docs are concise, linked, capitalize Kueue objects, and put what users look for first. New user-facing options are documented (README content also on the website).
- [ ] No typos or duplicated words, also in KEPs and docs (linters only check Go files).
- [ ] Validation errors use the matching `field.Error` type, one per problem.
- [ ] Optional config fields are pointers. Basic validation (positive counts, DNS names, MinItems) added.
- [ ] Feature gate checked first. Gate-off path does no extra work, allocation or metrics.
- [ ] Slice indexes that can be out of range are guarded and tested. No nil guards before map reads (a missing key reads as zero), but a pointer value from a map is still nil-checked before use.
- [ ] No in-place mutation of cache/snapshot data or input objects.
- [ ] In hot paths (scheduler, cache/snapshot, webhooks), static values computed once and no double lookups. No speculative optimization of code that isn't hot.
- [ ] Logic shared with other integrations is in a helper or tracked in an issue. A new optional job capability is its own `JobWith…` interface. Lifecycle methods (`IsActive`, `Finished`) match the operator's real states, with a comment on the mapping.
- [ ] Test values differ from defaults/quota so they prove the feature works. Each branch, both gate states and sibling input variants covered. Duplicate cases removed.
- [ ] Each test case changes only what it is about. Fixtures built with existing wrappers and suite setup, without redoing what they or zero values provide.
- [ ] Unit tests use `cmp.Diff` with `want...` objects (the whole `field.ErrorList` for validation). Test names match what is tested.
- [ ] KEPs: smallest scope, user-level motivation, reasons for claims, every new field explained, concrete test list, goals separate from requirements.
- [ ] Docs/website changes and unrelated follow-ups in separate PRs.
- [ ] Release note is `NONE` or specific and user-facing, behaviour changes called out, and the `kind` label is correct.
- [ ] During review: append commits, squash only when asked at the end.

## Method

- **Data.** All of this reviewer's PR and issue comments in kubernetes-sigs/kueue up to
  2026-11-24 (inline review comments with their diff hunk, review bodies, and
  top-level comments), each read together with the surrounding thread. Bot comments
  are excluded.
- **Analysis.** Theme shares come from keyword statistics over all of the reviewer's
  comments, checked by close reading of threads sampled across every year and area.
  Treat the shares as rough weights: themes overlap and keywords miss paraphrases.
- **Evidence.** Every quote is copied from the comment it links to, and each link was
  resolved through the GitHub API by matching the quote against that reviewer's
  comments on the PR. Quotes from PRs since deleted from GitHub were dropped.
- **Limits.** #1385 alone is 17% of reviewer comments, so the correctness, test and feature-gate rules lean on one PR with one author. KEP comments are many but discussion-like, so few become author rules. The data shows little about logging or upgrade safety. All quotes in Rules for authors were checked by script as exact substrings of a kerthcet entry body (raw corpus, 130 quotes; kind, date and path also matched). Kind/date/path come from the matching entry; where the same text occurs more than once, the earliest inline match is cited. Quotes keep the original typos and double spaces. Three precedents are issue comments (#485, #611, #973) and are linked as issues.
